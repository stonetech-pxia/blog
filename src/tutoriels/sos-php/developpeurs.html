En bref

  1. Passez à 8.2.35, 8.3.36, 8.4.27 ou 8.5.12 minimum, ou à un paquet de distribution qui inclut le correctif.
  2. Redémarrez tous les workers PHP (FPM, Apache, LiteSpeed, FrankenPHP, conteneurs).
  3. Vérifiez la version servie en HTTP, pas seulement php -v.
  4. Si vous ne pouvez pas mettre à jour tout de suite : appliquez les mesures provisoires ou mettez le service hors ligne.
  5. Une tentative d'exploitation a été observée le 17/10 : faites un contrôle de compromission.

Suis-je exposé ?

Toute installation PHP qui sert des requêtes web est concernée. Selon les avis officiels :

SAPIStatut d'après les avis PHP
Apache mod_phpRCE validée en HTTP avec la configuration par défaut. Priorité absolue.
PHP-FPMRCE validée via le cycle de vie des sessions. Exposition accrue si le frontal transmet PHP_VALUE / PHP_ADMIN_VALUE.
FrankenPHPProbablement vulnérable d'après l'analyse du code source.
LiteSpeed (LSAPI)Candidat conditionnel, exploitation non validée publiquement.
php-cgiCité comme concerné.
Serveurs applicatifs en CLI (Laravel Octane / Swoole / RoadRunner, php -S, artisan serve)Ils traitent des requêtes HTTP : par prudence, traitez-les comme exposés.
CLI seul (scripts, cron)Pas exposé aux requêtes web, mais mettez à jour quand même.

Configuration exploitée par la chaîne publique : session.upload_progress.enabled=On (valeur par défaut) et requêtes multipart acceptées. La faille se déclenche avant l'exécution de votre code : la qualité de l'application n'y change rien.

Diagnostic en 9 étapes

Pas de script à télécharger. Ce site n'en fournit aucun, et vous ne devriez exécuter aucun « outil de détection » trouvé en ligne. Chaque commande ci-dessous est standard, tient sur une ligne et ne fait que lire. Remplacez 8.2 par vos versions.

1. Quel système ?

cat /etc/os-release

Indique quelle section de mise à jour suivre (Debian/Ubuntu, RHEL, Alpine…).

2. Quelles installations de PHP existent ?

ls -d /usr/bin/php[0-9]* /usr/sbin/php-fpm* /opt/remi/php* /opt/cpanel/ea-php* /opt/plesk/php/* /opt/alt/php* 2>/dev/null

Chaque ligne est une installation à vérifier et à mettre à jour, même si le site ne l'utilise pas.

3. Quelle version pour chacune ?

php -v | head -1
for b in /usr/sbin/php-fpm* /opt/remi/php*/root/usr/sbin/php-fpm /opt/cpanel/ea-php*/root/usr/sbin/php-fpm; do [ -x "$b" ] && echo "$b : $("$b" -v | head -1)"; done

Les binaires FPM sont dans /usr/sbin, absent du PATH d'un utilisateur non-root sur Debian : d'où les chemins complets. php -v n'affiche pas toujours le suffixe de distribution (Debian l'omet, Ubuntu l'affiche) : la version exacte du paquet se lit à l'étape 4.

4. D'où viennent les paquets ?

dpkg -l | grep -E '^ii +(php|libapache2-mod-php)'     # Debian / Ubuntu
rpm -qa | grep -iE '^(php|ea-php|alt-php)'            # RHEL, cPanel, CloudLinux
apt-cache policy php8.2-common | head -4              # dépôt d'origine (adaptez la version)

+deb.sury.org = dépôt Sury / ondrej ; ~deb12u, ubuntu, .el9 = paquets de la distribution, qui peuvent contenir un correctif rétroporté.

5. Le correctif est-il dans le paquet ?

zgrep -E 'CVE-2026-10961[89]' /usr/share/doc/php*-common/changelog.Debian.gz           # Debian / Ubuntu / Sury
rpm -qa '*php*-common' | xargs -r rpm -q --changelog | grep -E 'CVE-2026-10961[89]'     # RHEL / Remi / cPanel

Une ligne affichée = correctif présent. Rien affiché : regardez le numéro de version. S'il est égal ou supérieur à la version corrigée, c'est corrigé (certains dépôts ne citent pas les CVE).

6. Quel PHP sert vraiment le site ?

ls /etc/apache2/mods-enabled/ 2>/dev/null | grep php                              # mod_php : quelle version (httpd -M sur RHEL)
grep -RhoE 'proxy:unix:[^|"]+' /etc/apache2/conf-enabled/ /etc/apache2/sites-enabled/ /etc/httpd/conf.d/ 2>/dev/null | sort | uniq -c  # Apache → socket FPM
sudo nginx -T 2>/dev/null | grep -v '^\s*#' | grep -oE '(server_name|fastcgi_pass)[^;]+'  # nginx : site → socket
systemctl list-units --type=service --all '*php*fpm*'                               # services FPM

Le socket (ex. php8.2-fpm.sock) indique la version utilisée par chaque site. nginx -T ne lit que la configuration active, sans les exemples commentés. Pour confirmer en HTTP, voir Vérification.

7. La mesure provisoire est-elle active côté FPM ?

/usr/sbin/php-fpm8.2 -i | grep -i 'upload_progress.enabled'      # cPanel : /opt/cpanel/ea-php82/root/usr/sbin/php-fpm -i
grep -r upload_progress /etc/php/*/fpm/pool.d/ /etc/php-fpm.d/ 2>/dev/null

Lit le php.ini de FPM (pas celui du CLI), puis les réglages des pools. Avec mod_php, seule la vérification en HTTP fait foi.

8. Des processus tournent-ils encore sur l'ancien code ?

sudo grep -l 'php.*(deleted)' /proc/[0-9]*/maps 2>/dev/null | cut -d/ -f3 | xargs -r ps -o pid,cmd -p   # partout
sudo needrestart -b              # Debian / Ubuntu (absent par défaut sur Debian : sudo apt install needrestart)
sudo dnf needs-restarting -s     # RHEL et dérivés

La première commande liste les processus qui utilisent encore des fichiers PHP remplacés par la mise à jour. Rien affiché = rien à redémarrer. Si php-fpm, apache2 ou httpd apparaît : redémarrez-le.

9. Et dans les conteneurs ?

for c in $(docker ps --format '{{.Names}}'); do echo "== $c"; docker exec "$c" php -v 2>&1 | grep -m1 '^PHP '; done

Un bloc par conteneur ; une version s'affiche s'il contient PHP.

Sur plusieurs serveurs

for h in web1 web2 web3; do echo "== $h"; ssh "$h" 'php -v | head -1; ls -d /usr/sbin/php-fpm* 2>/dev/null'; done
ansible all -m shell -a 'php -v | head -1'

Les pièges

1. Le correctif rétroporté : un numéro ancien n'est pas forcément vulnérable

Debian, Ubuntu et RHEL appliquent les correctifs sur leur propre version (par ex. 8.2.x-1~deb12uN). Comparer le numéro amont ne suffit donc pas : cherchez les CVE dans le changelog du paquet (commandes ci-dessous). Les distributions ont reçu les correctifs avant la publication.

2. php -v ment souvent

Le binaire CLI peut être à jour pendant que PHP-FPM, mod_php ou une autre version installée (/opt/remi, /opt/cpanel/ea-php*, /opt/plesk/php/*) sert encore le site. Sur un serveur multi-versions, chaque version installée doit être mise à jour.

3. Les anciens workers restent en mémoire

Tant que les processus ne sont pas redémarrés, l'ancien code tourne. Le reload suffit en général pour FPM, mais un restart est plus sûr. Pensez aussi aux conteneurs : un docker pull sans recréer le conteneur ne change rien.

4. Dépôt Remi

D'après Help Net Security (21/10), aucune mise à jour n'était disponible sur rpms.remirepo.net au moment de la publication. Vérifiez l'état du dépôt ; sinon, passez aux paquets de la distribution ou compilez depuis les sources.

5. Faux PoC

De faux exploits circulent sur GitHub, dont un avec une charge utile encodée en Base64. N'exécutez aucun PoC non vérifié, surtout pas sur la production.

Debian / Ubuntu (paquets de la distribution ou dépôt Sury / ondrej)

# État des lieux
sudo apt update
dpkg -l | grep -E '^ii +(php|libapache2-mod-php)'
apt list --upgradable 2>/dev/null | grep -i php
Dépôt ondrej / Sury ajouté sur Ubuntu ou Debian ? Il propose aussi les versions que la distribution fournit déjà (ex. 8.1 sur Ubuntu 22.04) avec un numéro plus élevé : la mise à jour ci-dessous remplacerait alors le paquet de la distribution par celui de Sury. Vérifiez d'abord quel dépôt sera utilisé (ligne Candidate) : 
apt-cache policy libapache2-mod-php8.1 php8.1-common | grep -E '^\S|Installed|Candidate'
# 1. Mise à jour de tous les paquets PHP installés (cli, fpm, mod_php, extensions…)
sudo apt install --only-upgrade $(dpkg -l | awk '/^ii +(php|libapache2-mod-php)/ {print $2}')
# 2. Le correctif est-il dans les paquets ?
zgrep -E 'CVE-2026-10961[89]' /usr/share/doc/php*-common/changelog.Debian.gz
# 3. Redémarrage de toutes les versions de PHP-FPM
sudo systemctl restart '*php*-fpm.service'
# 4. Seulement si mod_php (étape 6 du diagnostic)
sudo systemctl restart apache2

Puis l'étape 8 du diagnostic pour vérifier qu'aucun processus ne tourne sur l'ancien code.

  • Dépôt Sury / ondrej : le changelog cite en général les CVE ; à défaut, le numéro de version doit être au moins égal à la version corrigée de la branche.
  • PHP 8.1 sur Ubuntu 22.04 (ou toute branche fournie par la distribution) : la règle « 8.1 = migrer » ne s'applique pas tout de suite, car la distribution maintient sa propre version. Consultez son avis de sécurité (USN pour Ubuntu, DSA/DLA pour Debian) et vérifiez le changelog.

Windows / IIS

  1. Téléchargez la version corrigée sur windows.php.net (même variante NTS/TS et même architecture).
  2. Arrêtez le serveur web avant de remplacer les fichiers (sinon php-cgi.exe garde les DLL verrouillées et vous obtenez un mélange d'ancienne et de nouvelle version) : iisreset /stop (ou arrêt du service Apache).
  3. Sauvegardez le dossier PHP actuel et votre php.ini, remplacez les fichiers, gardez votre php.ini.
  4. Vérifiez que le Visual C++ Redistributable requis par la nouvelle version est installé, et que les mappages de gestionnaires IIS pointent vers le bon dossier.
  5. Redémarrez : iisreset /start.

PHP 8.1, 8.0, 7.4 et plus ancien

  • Ces branches ne sont plus maintenues par PHP. L'équipe de sécurité a publié des correctifs minimaux sous forme de code source pour 7.4, 8.0 et 8.1, à compiler vous-même.
  • Votre distribution ou un fournisseur de support étendu (Debian ELTS, TuxCare, Zend…) peut proposer un paquet corrigé : renseignez-vous auprès de lui.
  • À moyen terme : migrez vers 8.2 au minimum. Vérifiez d'abord la compatibilité (PHPCompatibility, Rector, journal des erreurs en préproduction).
  • Avant 7.4 : aucun correctif. Le centre de cybersécurité britannique (NCSC) recommande de mettre hors ligne tout système qu'on ne peut pas corriger rapidement.

Mesures provisoires (si vous ne pouvez pas mettre à jour tout de suite)

Aucune n'est complète. Elles réduisent l'exposition le temps de mettre à jour. Appliquez-les au niveau administrateur, puis redémarrez tous les workers. Un simple réglage dans php.ini ne suffit pas : ini_set() peut remettre une limite mémoire, et un .user.ini ou un .htaccess peut réactiver session.upload_progress. Utilisez php_admin_value / php_admin_flag, qui ne peuvent pas être modifiés par l'application. 
; Pool PHP-FPM, par ex. /etc/php/8.2/fpm/pool.d/www.conf (à répéter pour chaque pool)

; CVE-2026-109619 : chemin des sessions
php_admin_flag[session.upload_progress.enabled] = off

; CVE-2026-109619 : PHP 8.5 uniquement
php_admin_flag[fatal_error_backtraces] = off

; CVE-2026-109618 : mitigation principale (retire la protection contre l'épuisement mémoire)
php_admin_value[memory_limit] = -1

; Casse la condition « même worker » (coûteux en performances)
pm.max_requests = 1

Avec mod_php : mêmes directives sous la forme php_admin_flag session.upload_progress.enabled off dans la configuration Apache (pas dans .htaccess).

Compensez memory_limit = -1 par une limite au niveau du système, sinon une seule requête peut épuiser la mémoire et faire tuer d'autres services (base de données comprise). N'utilisez pas RLIMIT_AS / RLIMIT_DATA :

sudo systemctl set-property php8.2-fpm.service MemoryMax=2G   # adaptez la valeur et le nom du service

Autres mesures citées par les avis :

  • Garder post_max_size bas et limiter la taille des requêtes au niveau du frontal (nginx, proxy, WAF).
  • Réduire max_input_nesting_level et le nombre de variables et de parties multipart.
  • Si l'application n'utilise pas de formulaires multipart (envoi de fichiers), bloquer ces requêtes avant PHP. Exemple nginx, dans le bloc location ~ \.php$ : 
    client_max_body_size 1m;
if ($http_content_type ~* "multipart/form-data") { return 403; }
  • Ne pas laisser le frontal transmettre PHP_VALUE / PHP_ADMIN_VALUE à FPM.
  • Cloudflare a déployé des règles WAF pour les vecteurs connus : utile, mais ce n'est qu'un pansement.

Vérification

Contrôlez la version réellement servie. Créez un fichier temporaire au nom imprévisible dans la racine web du site. D'abord, indiquez cette racine (modifiez le chemin avant de copier) :

DOCROOT=/var/www/monsite/public   # racine web du site (dossier public/ pour Laravel / Symfony)
f="v-$(cat /proc/sys/kernel/random/uuid).php"
echo '<?php header("Content-Type: text/plain"); echo PHP_VERSION, " ", PHP_SAPI, " upload_progress=", ini_get("session.upload_progress.enabled") ? "On" : "Off";' \
  | sudo tee "$DOCROOT/$f" >/dev/null
echo "Ouvrez : https://votre-site/$f"

Notez le résultat, puis seulement supprimez le fichier (dans le même terminal) :

sudo rm -- "$DOCROOT/$f"

Laravel / Symfony avec nginx (seul index.php est servi) ou plusieurs pools FPM : interrogez chaque socket directement, sans rien déposer dans le site. Le fichier de test est placé dans /dev/shm, visible par FPM même avec PrivateTmp (RHEL). Un open_basedir peut toutefois le bloquer.

sudo apt install libfcgi-bin   # fournit cgi-fcgi (RHEL : dnf install fcgi, dépôt EPEL)
echo '<?php echo PHP_VERSION, " upload_progress=", ini_get("session.upload_progress.enabled") ? "On" : "Off", "\n";' | sudo tee /dev/shm/v.php >/dev/null
for s in /run/php/*.sock /run/php-fpm/*.sock /opt/cpanel/ea-php*/root/usr/var/run/php-fpm/*.sock; do [ -S "$s" ] && [ ! -L "$s" ] && echo "$s : $(sudo SCRIPT_FILENAME=/dev/shm/v.php REQUEST_METHOD=GET cgi-fcgi -bind -connect "$s" | tail -1)"; done
sudo rm /dev/shm/v.php

Enfin, l'étape 8 du diagnostic confirme qu'aucun processus ne tourne encore sur l'ancien code.

Contrôle de compromission

Aucun indicateur de compromission officiel n'a été publié à ce jour. Ce sont des vérifications d'hygiène générale, à faire depuis le 15 octobre par prudence :

# Fichiers PHP créés ou modifiés depuis le 15/10 (ctime : ne peut pas être falsifié avec touch)
# Les caches de templates (ex. storage/framework/views) sont exclus : ils changent en permanence
sudo find /var/www /home /srv -type f -name '*.php' -newerct '2026-10-15' \
  -not -path '*/storage/framework/*' -not -path '*/var/cache/*' 2>/dev/null > ~/php-modifies.txt
wc -l ~/php-modifies.txt

# Fichiers PHP dans les dossiers d'upload, et fichiers suspects dans /tmp et /dev/shm
sudo find /var/www /home /srv -type f -name '*.php*' -path '*upload*' 2>/dev/null
sudo find /tmp /var/tmp /dev/shm -type f -newerct '2026-10-15' 2>/dev/null

# Rafales d'erreurs fatales mémoire (la faille repose sur des erreurs fatales / OOM), journaux archivés compris
# (sudo sh -c : les jokers doivent être développés par root, /var/log/httpd n'est pas lisible sinon)
sudo sh -c "zgrep -h 'Allowed memory size' /var/log/php*-fpm.log* /var/log/php-fpm/* /var/log/apache2/error.log* \
  /var/log/httpd/error_log* /var/log/nginx/error.log* /etc/apache2/logs/error_log* \
  /opt/cpanel/ea-php*/root/usr/var/log/php-fpm/* 2>/dev/null" | tail -50
# (avec nginx + FPM, ces erreurs apparaissent aussi sous la forme « FastCGI sent in stderr » ;
#  sur cPanel, chaque site peut aussi avoir son propre fichier error_log)

# Tâches planifiées, comptes, clés SSH
sudo ls -la /etc/cron.* /var/spool/cron/crontabs /var/spool/cron 2>/dev/null
sudo crontab -l -u www-data 2>/dev/null   # (apache ou nginx selon la distribution)
awk -F: '$3 == 0 {print "uid 0 :", $1}' /etc/passwd
awk -F: '$3 >= 1000 {print $1, $6, $7}' /etc/passwd
sudo find / -name authorized_keys -newerct '2026-10-15' 2>/dev/null

# Connexions établies hors ports de service locaux (le port 443 distant n'est PAS exclu : les C2 l'utilisent)
sudo ss -tnp state established '( sport != :22 and sport != :80 and sport != :443 )'

Au moindre doute : isolez le serveur, conservez les journaux, changez les secrets (base de données, clés d'API, mots de passe administrateur) après avoir corrigé PHP, et faites appel à un spécialiste.
